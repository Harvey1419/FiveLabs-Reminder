### Resulting architecture

1. The existing model emits a canonical decision, including the response language, optional explicit profile changes, and per-action continuation fields keyed by the persisted `callId`. Main turns, approvals and continuations all receive strict structured-provider validation, including completion status. Semantic regex for action claims, language selection and profile timezone updates was removed from the foreground path.
2. Authored input is separate from quoted/OCR evidence and appears last in the model request. A profile update requires an exact source quote in that authored input, a valid IANA timezone/language, and a matching persisted result. Merely speaking another language changes the response language, without silently persisting a preference.
3. Pending actions retain their full payload, original temporal anchor and individual fields. Corrections can replace an approval through the canonical parser. Ambiguous or incomplete answers keep the draft pending; unrelated work cannot silently overwrite it. A conditional owner/status/expiry update claims a pending run before tools execute.
4. Tool outcomes produce execution facts. Pre-execution conversational success prose is excluded from operational confirmations. Partial successes remain visible; exceptions and malformed results become unknown outcomes, stop later actions and prevent automatic replay of that pending run. Approvals also persist a write fence before each effect.
5. Fresh and resumed operations share working-memory update rules. Task updates/deletions preserve displayed identities and tombstones instead of replacing the list with the last returned item or labeling everything as newly created. Fresh creation batches retain every created identity, including after restoring conversation state from the database.
6. A derived question about read results can request one bounded observation step using the same model. It receives only observed read data, has no write tools, validates cited call IDs, and retains verified cards if synthesis fails. It does not calculate from the truncated overview. Memory retrieval likewise retains a successful search channel when the other fails and explicitly reports partial availability.

7. Webhook ingress persists each message in `hermes_inbound_turns` before HTTP 200. A message ID is unique; database claims serialize each recipient across replicas while allowing independent recipients to progress. Renewable ownership tokens fence tools, database requests and delivery. Queued messages survive restarts; expired running turns become `unknown` and are never automatically replayed. The response and execution facts are checkpointed before delivery; the provider receipt is merged afterward.
8. All WhatsApp message formats share one delivery boundary. Network interruption, HTTP 5xx or a missing provider message ID produces an unknown outcome. Only explicit rate-limit rejection permits retry; an explicitly rejected interactive format can fall back to text on the same originating channel. Button mutations require observed owned rows, expose partial companion updates, and use stored response-language metadata. UUID acknowledgment is owner-qualified. Foreground profile reads bypass stale replica caches.
9. Railway now has a `/health` deployment check, a pinned package-manager version, required configuration/schema checks before listening, and bounded graceful shutdown. Supabase application tables and RPCs are restricted to the backend service role; public/authenticated access was removed while preserving backend access.
